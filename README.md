# Angular Beer Game

A standalone Angular 21 application with Single Player and Multiplayer modes. Choose Retailer, Wholesaler, Distributor, or Manufacturer and manage orders across a 24-week supply chain simulation. Single Player automates the remaining three parties; Multiplayer connects 1–4 human players over WebRTC and automates unassigned roles.

The animated supply-chain scene shows customer visits, delivery trucks, incoming and outgoing crates, and exact weekly activity counts. Order links show the one-week delay; delivery links and manufacturer production show two weeks. Each party has a delivery schedule with quantities due over the next two weeks. Each submitted week plays once in a six-second sequence: arrivals, dispatches, then upstream orders. **Pause animation** / **Resume animation** control only that week's playback, never the simulation or other players; the scene stays still between turns. Order links show quantities and the week they will reach the supplier. The order form appears above the scene. Crates are symbolic, and system reduced-motion preferences disable movement. On narrow screens, the illustrated chain scrolls horizontally.

## Run

Use Node.js 22.12+ or 24 and npm (or pnpm).

```sh
npm install
npm start
```

Open http://127.0.0.1:4200. `npm start` starts both Angular (4200) and the signaling service (8787); Angular proxies signaling requests. Stop existing processes using those ports first. With pnpm, use `pnpm install` and `pnpm start`. The included pnpm lockfile records the verified dependencies.

If using `ng serve` directly, start `npm run start:server` in another terminal first. The proxy is also configured in `angular.json`, so plain `ng serve` forwards `/rtc-config` and `/signaling`. Restart an already-running Angular server after changing proxy configuration. An HTML/JSON error during room creation usually means the configuration request reached the frontend instead of the signaling service; the app now explains how to fix this rather than showing a raw JSON parser error.

```sh
npm run build
npm test
```

Build output: `dist/beer-game/browser`.

For a built app, run `npm run serve` and open http://127.0.0.1:8787. Build before running the test suite; the server integration test verifies the built application's HTTP response.

## Multiplayer

1. Choose Multiplayer → Create a supply chain, then Team Supply Chain (one shared chain, a different role for each player), Classroom Individual Challenge (independent runs of the same role and demand) or Classroom Group Challenge (groups of up to four, each playing its own chain with the same demand), enter a name, and create it. Steps (Game type, Settings, Invite and start) show progress, and Back keeps unfinished fields.
2. Share the six-digit numeric code (**Copy code**), the invitation link (**Copy invitation link**, or **Share invitation** on phones with a share sheet, falling back to copying) or the QR code. If the QR code cannot be drawn, the link and code stay visible. Players can join from the home screen and then enter a unique nickname (**Save nickname**). Code fields ignore spaces, dashes and dots ("295 384" becomes 295384), keep leading zeros and accept a pasted invitation link to the same site; anything else is refused. Invitation links also prefill the code. On phones a joining player sees nickname, role and readiness first, with the code, QR and link under **Invite others**; the host sees the invitation first.
3. The host and each joining player select one available role. Until the game starts a player can switch to any role nobody holds; the server handles each claim whole, so two players never hold the same role. Taken roles show their owner ("Taken by Alex") and stay reachable by keyboard but cannot be chosen; on phones the roles are compact rows. Before game start, a departing player's role becomes available again.
4. The host can start alone or with up to three guests. Each joined player must enter a nickname, choose a role and have an open WebRTC connection to the host. The participant list shows each player's state (Enter nickname, Choose role, Connecting, Ready, or Disconnected — can resume), and a summary beside Start names every current blocker, for example "1 of 2 players ready · waiting for Alex to choose a role". Transport details are under **Connection details**. Beside Start the host sees a review: mode, visibility, the players' roles and the roles the system will play (a Classroom shows the shared role, demand method and seed). Guests see the unclaimed roles once nobody is still choosing; no four-human minimum applies. For a disconnected lobby member the host can select **Remove**, or, when nothing else blocks the start, **Start without Alex** ("Start without Alex? Their role will be played by the system."): a Team member with a nickname and role keeps the seat, the system plays it as if they had left, and they take it back from the week after they return; anyone else, and any Classroom competitor, is removed. A removed player is told why when they try to resume. The roster is then fixed, except for the departure decisions below. A failed start is explained beside the Start button, and nickname, code and order errors appear beside their fields. A failed join says what to do next: an unknown code, an ended game or a full lobby (both with **Create a game**), or a game that has already started, where **Resume game** appears only if this browser holds a save for that game; the public invitation never grants a place.
5. Human players submit a whole-number order (0–100) per week. The host advances the shared engine after all human orders arrive, using the existing automated policy for system roles, and broadcasts the resulting state over WebRTC. Submitted human orders are locked for the turn. Metrics, animation, ledger and exports remain available for each player's role.

The topology is host-to-up-to-three-guests. WebSockets carry room membership, role reservations and WebRTC SDP/ICE signaling. Weekly orders and game snapshots use ordered WebRTC data channels exclusively. No camera or microphone is used. The host is the authoritative coordinator and should remain connected for the full session. Human roles are set at start; late joining or taking over a system role during play is not supported. A Team guest who leaves a started game, or stays disconnected for about 60 seconds, keeps their seat, and play waits for them. A message in the game then asks the host: "Alex (Wholesaler) has left. Let the system play Wholesaler, or keep waiting?" If the host is offline, any connected player can answer; the first answer counts, everyone sees who decided, and play continues when the host returns. The system plays from the week the game is waiting on, keeping any order the player already sent, and the station is labelled System (Alex left). A returning player takes the role back from the next week. A host who leaves ends the game; there is no host migration.

### Connecting other devices

Localhost invitations are for tabs on the same computer. For phones or remote players, host the built app and signaling service behind a shared HTTPS address with WebSocket upgrades forwarded for `/signaling`; route `/rtc-config` to the same service. Invitation links use the browser's current origin. HTTPS provides the secure context required for remote WebRTC usage.

The Node server defaults to loopback on port 8787. Configure `HOST` and `PORT` for your deployment; binding to `0.0.0.0` exposes the service on the host network and does not provide TLS by itself. Use an HTTPS reverse proxy for remote devices.

ICE configuration is supplied at runtime via these server environment variables:

- `STUN_URLS`: comma-separated STUN URLs (default `stun:stun.l.google.com:19302`, or `stun:stun.cloudflare.com:3478` when Cloudflare TURN is configured).
- `CLOUDFLARE_TURN_KEY_ID`, `CLOUDFLARE_TURN_KEY_API_TOKEN`: a Cloudflare Realtime TURN key, for networks where direct connections fail. The server requests short-lived credentials for a room member only once they have someone online to connect to (the host: any guest; a guest: the host), never for a player alone in a room, and sends them over the signaling socket before the messages that create peer connections, so every peer can use the relay; `/rtc-config` never contains them. It revokes them when no longer needed: when the player disconnects, leaves or is removed, their reservation expires, the room closes, a resume replaces them, or the results are revealed. Requests time out after 3 seconds (the player then continues with STUN only) and are limited to one per connection and 120 a minute. Keep the API token private. `node --env-file=.env scripts/check-turn.mjs` checks the key and revocation without printing credentials (see docs/DEPLOYMENT.md).
- `TURN_TTL_SECONDS`: lifetime of each player's Cloudflare credentials (default 10800, 3 hours). A relayed connection can drop once its credential expires; Reconnect, or a refresh and Resume, fetches fresh ones.
- `TURN_URLS`: comma-separated TURN/TURNS URLs of a static relay (cannot be combined with Cloudflare TURN; the server refuses to start).
- `TURN_USERNAME`, `TURN_PASSWORD`: static relay credentials. `/rtc-config` delivers these to every connecting browser; use limited-lifetime credentials for a public deployment.

Rooms live in server memory. Each multiplayer game this browser creates or joins is saved in local storage under its own key (room and member), including a private reconnect token; hosts also save authoritative engines, pending orders and classroom results. Up to 5 multiplayer games are kept: a sixth replaces the least recently saved one that no other tab has open. An unfinished single-player game is saved after each week and comes straight back when you refresh that tab. When saves exist, **Your games** lists them at the top of the page (never over a game in progress). Each multiplayer row is checked with the server: Checking…, Available, Couldn't verify (with Retry; a network failure never removes a save), or the reason it ended (for example "The host removed you before it started."), which stays until you select OK. A game open in another tab of this browser reads **Open in another tab** and offers nothing until that tab closes; tabs tell each other over a BroadcastChannel, and storage events keep every tab's list current. **Resume game** recovers your identity, nickname, role and progress, and **Remove** clears only this browser's copy. A host's save also offers **End game for everyone**, which resumes with the saved token and leaves, so its players are told at once; removing a host's save without ending it asks first, because its players would wait until it expires. Creating or joining another game never replaces a save, so nothing is asked. If the connection drops during a session, **Reconnect** beside the Connection lost message rejoins with the same identity and pending orders. A guest whose order is waiting sees when the host is offline, and an order that never reached the host is sent again once the connection returns. Disconnected memberships, and Team guests who leave a started game, are reserved for 24 hours; the host must return before play can continue. Explicitly leaving as host ends the room, and server restarts invalidate saved sessions. The end-of-game reveal (in a classroom, once every run is over) removes the browser save; a finished classroom run that is still waiting for the reveal can be resumed. A finished game still admits its players for 30 minutes while its host is online, so a player who was away at the end (for example mid-refresh, or a student who finished early and closed the page) receives the final results when they resume; after that the server forgets the room. A failed create or join keeps every save. Team play pauses for missing players until they return or the system is chosen to play their role; classroom competitors continue independently when another guest disconnects. Classroom time includes disconnections. Host migration, cross-device recovery, late joining and database persistence are not implemented. Storage must be available. Six-digit invitation URLs (/multiplayer/join/295384) and lobby QR codes open a prefilled join form; mobile devices need a reachable hosted or LAN address, not localhost.

## Classroom challenges

Multiplayer creation offers Team Supply Chain (the shared 1–4 player game above), Classroom Individual Challenge (up to 32 participants, including the host; it keeps the /multiplayer/classroom-challenge address) or Classroom Group Challenge (below). The host chooses everyone's role, visibility, integer demand seed and scenario method: 3-week simple moving average, weighted moving average with weights 1:2:3, or an 8-week cyclic pattern. Seeded variation produces a reproducible teaching scenario. These are scenario generators, not forecasts of external sales. Each competitor receives the same demand at the selected role and plays an independent 24-week run with system roles.

Join using the six-digit code, enter a unique nickname, and wait for the host to start. The host may start with any number of ready participants. Results rank completed runs by the player's cumulative cost ascending, then elapsed milliseconds from the common start until the host receives the final order. Waiting and network latency count toward time. Leave the results screen open for live leaderboard updates; the host must remain connected until everyone finishes. Above the leaderboard, counts show how many players are playing, disconnected, finished and incomplete, and the host sees their own connection (online or lost). One line explains the order: unfinished players are ordered by progress, finished players ranked by cost, then time. With 10 or more players, **Find a player** and a **Status** filter appear; ranks stay those of the whole class, and rows that move never take keyboard focus with them. On phones the leaderboard becomes compact cards with the name and progress on the first line. Incomplete players remain unranked. If someone drops out, the host (playing or host only) can select **Finish classroom**: unfinished runs stop, show as Incomplete in the leaderboard and get a final Classroom finished screen, and everyone's results are revealed. Weekly holding/backorder charges for the last completed week and their per-case rates appear beside current demand.

### Classroom Group Challenge

Create it at /multiplayer/classroom-group-challenge. The host sets visibility, demand seed and method, and only hosts: there is no participation choice and no shared role. The room holds 32 people including the host, so at most 8 groups of up to 4. After joining with the code and a nickname, a player sees every group (name, members with their roles, free places) and either selects **Create a group** (a name unique in the room, whatever its case) or **Join** a group with a free place. Until the host starts, a player can **Switch to** another group, which frees their old role, and choose any role nobody in their group holds; roles nobody chooses are played by the system. The server handles each create, join, switch and role claim whole, so a group never has five members or two players in one role. The participant list and the summary beside Start name each blocker ("waiting for Alex to join a group"), the review lists the groups and any empty ones, which are dropped at start, and **Remove** and **Start without** work as in Team (a disconnected member keeps the seat only beside a group-mate who stays). At least one group with a ready member is needed; rosters are then fixed.

The host runs one Team engine per group, all with the same seeded customer demand. Each group advances once its own human members have all ordered, exactly like a Team game: visibility applies per role, orders are acknowledged, and a member who leaves is handled inside the group (the host sees the prompt, named after the group, above the leaderboard; a group-mate can answer while the host is offline). If the system ends up playing every role of a group, that group plays on to week 24 at once. The live leaderboard lists groups with their members, progress, total chain cost (all four roles, including system-played ones) and time; groups rank by cost, then by time from the shared start until they complete week 24. Find and filter appear once 10 or more players are in groups, and phones show cards. Players see their group's status chips and the group leaderboard. **Finish classroom** marks unfinished groups Incomplete. Once every group is over, each member sees their own group's full chain and debrief, never another group's. The host's checkpoint holds every group's engine and pending orders, and a player who refreshes resumes into their group.

The 32-player cap is a functional limit, not a tested concurrency guarantee. Five-player integration coverage verifies independent progression and live results, and a real-browser test runs a 32-player leaderboard with 31 simulated competitors (real signaling and WebRTC) in one browser. The host is trusted, seeds are public, and this is not a tamper-resistant examination system. Codes are randomly generated with collision checks; basic per-connection join throttling is not production authentication or abuse protection. Restart the app/signaling server after upgrading; previous long-format codes are no longer accepted.

## AI players via MCP

The local stdio MCP server in `mcp/index.mjs` lets AI clients play Single Player or create/join Multiplayer chains alongside people. Each session controls one role in the actual Angular app; multiplayer gameplay continues to use WebRTC. It provides tools for rules, game state, lobby start, weekly orders, waiting, history, CSV and session cleanup.

See [MCP setup and playing workflows](mcp/README.md) and [example client configuration](mcp/client.example.json). Start the app server first, configure an installed Edge/Chrome browser or install Playwright Chromium, and connect the MCP client to the script. Set `BEER_GAME_HEADLESS=false` to watch the AI's browser. This is a local stdio integration; remote HTTP MCP hosting is not included.

## Simulation rules

- Each party starts with 12 cases in stock, no backlog, and two shipments of 4 cases in transit. Upstream parties have an initial order of 4 pending.
- Customer demand is 4 cases in weeks 1–4 and 8 cases in weeks 5–24.
- Each turn receives deliveries, receives downstream demand, ships as much as available (including previous backlog), places orders, and charges costs on ending stock and backlog.
- Orders reach the upstream party next week. Shipments arrive two weeks after dispatch. Manufacturer orders enter its two-week production pipeline.
- Inventory costs $0.50 per case per week; backlog costs $1.00 per case per week.
- Automated parties target five weeks of latest demand in their inventory position: three weeks on hand and two in transit. Inventory position is stock plus shipments in transit minus backlog. Orders are capped at 100, as are player orders.
- During play, operational data and CSV records follow the selected information visibility level; hidden information is revealed once the game is over (see [After the game](#after-the-game)). Network Wide shows all four parties; Dyadic shows your own and directly adjacent roles; None shows your own role only. Single-player games stay in memory and reset on refresh or a confirmed New game. Browser Back, Forward and the logo keep any game in progress and show a Return to game bar. Multiplayer sessions support same-browser refresh recovery as described above.

The simulation engine is independent of Angular in `src/app/game.ts`. Tests verify steady state, lead times, conservation, costs, input validation, game completion, four-party human orders, room credentials, role locking and signaling isolation. This is an educational variant, not a port of the adjacent AnyLogic model.



## Game view

Use the plus/minus buttons or type a weekly order. The field is labelled with the week you are deciding (Order for week 4), while the board says which completed week it shows (Showing completed week 3). In multiplayer, the line under the order button tracks your order: the button reads **Sending…** until the host replies, then **Accepted for week 4: 7 cases. Waiting for Alex and Sam.** The field keeps the amount you sent and says why it is locked (Locked until confirmed, or Locked until week 5). If the host has not replied after 5 seconds, **Send again** re-sends the same order; if the connection drops first, the line says **Connection interrupted** and the order goes again once you reconnect. The host accepts at most one order per role (in a classroom, per run) per week, so a re-sent order never plays a week twice. On-hand inventory, unfilled backlog, in-transit arrivals and cumulative cost stay visible with their weekly changes: inventory changes are neutral, a rising backlog or cost is shown as adverse, an unchanged value reads No change, and cost shows this week's charge (This week: $6.00). Open **Explore the full story** for permitted-role summaries, charts, the ledger and CSV export; open **Delivery schedule & lead times** for delivery details. These two detail panels start collapsed. Small ⓘ buttons beside your role, this week's demand, the weekly costs, backlog and in transit open a short explanation of the rules there (closed by default; they never show hidden data or suggest what to order), and the role choice has one for all four roles. Collapsing panels does not reduce MCP responses; the explicit visibility policy applies consistently to both UI and MCP.

The desktop game view now places a vertical Manufacturer → Distributor → Wholesaler → Retailer animation on the left, with compact order controls and all four main metrics on the right. Other statistics remain in the collapsed bottom section. On narrow screens (860px and below) the page follows the play order instead: a compact header (role, week, cost, a one-line visibility chip), one turn card with this week's demand, last week's costs and the order controls, the week result with a **Watch week N ↓** link, team status or the classroom leaderboard, the main metrics, then the board. The board can be hidden on narrow screens but starts open, so each week's animation still plays once. The app uses the device's system font, so no font files are downloaded. Game stats' trend chart has a value axis in cases and tells inventory, backlog and orders apart by colour, line pattern and marker shape; the weekly ledger keeps the exact values.

For keyboard and screen-reader users, a **Skip to main content** link is the first Tab stop, focus moves to the new heading after each setup route change, single-player roles are a radio group, and each week is announced once ("Week 3 complete. Week 4 demand: 8 cases.") instead of the demand card, week result and board caption each announcing. On phones and touch screens, buttons, standalone links and disclosure summaries are at least 44px tall where practical (links inside text, such as the invitation URL, are not).

When the game is over, the completion screen adds a debrief: a bullwhip chart of each role's weekly orders against customer demand (roles are told apart by colour, line pattern and marker shape, with a weekly table as an alternative), each role's order swing (standard deviation of its orders ÷ standard deviation of customer demand) and peak backlog, and the holding and backlog cost split for every role and the team, which adds up exactly to the game's costs. Downloaded CSV names include the room name and code (or the standard scenario), the role and the date, for example `beer-game-sydney-class-482913-retailer-2026-10-11.csv`.

## Information visibility

The starting screen explains three levels. Network Wide is the initial default. Choose a level before starting single-player, or in **Create your supply chain** for multiplayer. The room choice is fixed at creation; joining players inherit it and cannot override it. The lobby and game display the selected level.

| Level | Operational information visible |
| --- | --- |
| Network Wide (`network`) | All four roles, including team cost. |
| Dyadic (`dyadic`) | Your own role and immediate supplier/customer roles. Retailer sees Retailer/Wholesaler; Wholesaler sees Retailer/Wholesaler/Distributor; Distributor sees Wholesaler/Distributor/Manufacturer; Manufacturer sees Distributor/Manufacturer. |
| None (`none`) | Your own role only. None means no sharing across roles. |

The policy covers stock, backlog, order quantities, deliveries, lead-time displays, costs, history, CSV and quantity-driven animations. Hidden roles retain their names/buildings for orientation but show no operational quantities. Team cost is hidden in restricted modes, and customer-demand data is hidden when Retailer is outside the visible set. Common simulation rules, chain topology, member roles and order-submission status remain public so players can coordinate. Lead times for routes involving a visible role remain available.

### After the game

Hidden information is revealed once the game is over: in single-player and Team games as soon as week 24 completes, and in either classroom mode only once every competitor or group has finished (or the host selects Finish classroom), so a finished player cannot pass the remaining demand to classmates who are still playing. Each player then sees their own supply chain in full: every role's stock, backlog, orders and costs, customer demand and the team total. In a classroom this is the player's own run, including its system-played roles, never other students' runs; in a group challenge it is their group's chain, never another group's. The host sends one final unfiltered snapshot (each classroom competitor receives their own full history), revealed values are labelled **Revealed after the game**, and the debrief, Game stats, CSV export and MCP state all show the same data. Before the reveal nothing changes. A player whose run is over keeps the final screen when the host closes the room.

MCP tools preserve all fields for permitted roles. Optional `visibility` on create tools selects the policy; the join tool inherits the room policy. Restricted guests receive filtered WebRTC snapshots rather than hidden data merely being concealed in the UI. The host remains the trusted simulation authority: its browser must retain the full engine internally, though its UI, MCP responses and exports are filtered to its player role. This is an educational visibility policy, not protection against a host inspecting or modifying their own engine. All participants should use the updated app; restart the signaling server after deploying this feature.

### Hosting without playing

In Classroom Individual Challenge creation, choose **Host only** under Your participation to watch the live leaderboard instead of playing; a Classroom Group Challenge host always hosts only. **Play and host** remains the default. At least one competitor must join before a host who is not playing starts. They have no player role, game controls or score entry. Progress and cumulative costs update after each player's week; finished players rank by cost, then completion time. The host must keep the page open to coordinate WebRTC games. The 32-person room cap includes the host.

### Docker image

Build and push one image for both Intel/AMD (`linux/amd64`) and ARM (`linux/arm64`) servers from the project folder. Use a new tag for each release so servers pull the new image.

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t <your-registry>/beergame:0.0.2 --push .
```

The container needs `PUBLIC_ORIGIN` set to the site's exact `https://` address. Any reverse proxy in front of it must forward WebSocket upgrades on `/signaling`.
